# Executable project planning

## 何时触发

- 制定项目方案或版本计划。
- 编写供 Codex 执行的跨文件任务书。
- UI 全局改造或跨页面修改。
- 重构、数据迁移、架构调整。
- 修改跨越多个组件、路由、样式入口或数据流。

## 何时不触发

- 单个拼写修复。
- 单行配置修改。
- 单个明确错误，且修改边界已经完全确定。
- 已有完整文件级任务书，只需机械执行。
- 只解释概念而不修改工程。

## 规划模式与实施模式

1. 用户只要求方案、计划、审计或任务书时，进入规划模式。
2. 规划模式只能读取真实工程、修改用户明确授权的计划、审计或 Skill 文件，并运行用户授权的只读检查或质量检查。
3. 规划模式不得修改业务代码、产品页面或数据，不得安装依赖，也不得自动进入实施。
4. 输出计划后立即停止，等待用户明确批准；计划本身不构成实施授权。
5. 只有用户明确要求执行已批准计划时，才进入实施模式。
6. 实施模式开始时仍须重新检查真实分支、提交、工作区和文件结构，并核对计划与当前工程是否存在偏差；发现偏差时先停止并汇报，不得机械套用旧计划。

## 执行步骤

1. 完整读取 `docs/ALEKSI_CODEX_PLANNING_METHOD.md`、仓库 `AGENTS.md`、当前路线图和本次阶段边界。
2. 先执行只读基线检查，记录工作区、分支、提交、实际脚本和禁止范围；不满足前置条件时停止。
3. 使用真实文件列表遍历工程，再读取入口、路由、公共组件、页面组件、样式、数据流、测试、构建与文档；不得根据需求文字猜测路径存在。
4. 明确区分产品问题、视觉问题、交互问题和工程问题；每个问题写出实际文件、表现、影响和根因。
5. 先找全局根因，再处理局部表现；优先复用现有组件、数据流、样式入口、路由模式和测试结构。
6. 写出必须保留的结构与不得再创建第二套的实现，避免用新文件掩盖现有结构问题。
7. 对每个阶段给出修改前必须读取的真实文件、逐文件修改要求，以及允许新增文件的单一职责、输入、输出、调用方和新增理由。
8. 按工程依赖排列执行顺序：先契约与纯逻辑，再组件和页面，再样式与测试，最后全局回归；不得先把全部逻辑堆入 JSX。
9. 提供数据和状态流，写清输入、纯函数、组件、查询参数读写、刷新、浏览器前进后退和目标路由。
10. 提供需求—文件—测试映射、相关页面的全局回归范围、停止条件、可运行验收标准和阶段禁止事项。
11. 运行任务授权的 lint、类型检查、测试、构建、空白检查与 Git 检查；如实记录失败，不用关闭规则或删除测试换取通过。
12. 实施结束后核对实际 diff 与计划；报告只能说明结果，不能代替真实实现。

## 计划的最低输出结构

- 任务目标、项目定位和主链路。
- 真实工程基线与已读取文件。
- 产品、视觉、交互、工程四类问题。
- 必须保留和必须复用的现有能力。
- 每个阶段的目标、修改前必读文件、逐文件修改表、允许新增文件表。
- 每个阶段的数据与状态流、依赖顺序、需求—文件—测试映射。
- 相关全局回归范围、停止条件、验收标准和禁止事项。
- 重要结论引用真实文件路径；不存在的文件必须明确标为“允许新增”，不得伪装成现状。

## 安全边界

- 不猜测文件路径、组件、接口、数据结构或已有功能；无法从仓库确认时明确写“未知”并停止相关假设。
- 不创建重复公共组件、第二套数据流、第二套样式系统或覆盖式热补丁。
- 不因任务较大而擅自拆成多个互不完整的交付；阶段划分只能表达依赖和验收门。
- 不新增无必要依赖，不越过路线图阶段，不擅自修改产品决策、凭据、外部系统或用户数据。
- 不使用 README、总结或报告代替实际实现，不把计划中的未来文件描述为已经存在。
- 发现计划与真实结构不一致、需要越权文件、需要生产依赖、验证失败或产品决策冲突时停止并汇报。

## Git 与用户工作保护

1. 工作区不干净时，必须先停止并汇报具体变化，不得假设这些变化可以覆盖或清理。
2. 不得自行丢弃、覆盖或删除用户已有修改。
3. 未获得用户明确授权时，不得执行 `git reset --hard`、`git clean -fd`、会覆盖用户工作的 `git restore`、`git stash apply`、`git stash pop`、`git stash drop` 或 `git stash clear`。
4. 已有修改应当保留、备份、恢复还是删除，必须由用户决定。
5. 目标分支已存在时不得覆盖或删除；应停止并报告分支冲突。
6. 合并失败或无法 fast-forward 时不得自行创建普通合并提交、变基或以其他方式改写历史。
7. 计划、实施和验收任务都不得使用 Git 清理命令掩盖越界修改或制造虚假的干净状态。

## 输出要求

- 输出必须达到文件级粒度，避免“优化一下”“完善页面”“适当重构”等不可验证描述。
- 新文件必须有单一职责和不可由现有文件承担的理由；不需要新增时明确写“本阶段不新增文件”。
- 每项主要需求必须能追溯到实现文件、测试文件、自动验证和人工验收。
- 验收标准必须可运行、可观察、可测试；明确记录全局遍历、整体一致、避免热补丁、避免技术债、复用现有结构和主动运行验证。
- 明确说明不以总结文件代替实际实现，也不因任务范围大而擅自拆成多个互不完整的交付。

## Codex 八荣八耻

Codex八荣八耻
以瞎猜接口为耻、认真查询为荣；
以模糊执行为耻、寻求确认为荣；
以臆想业务为耻、人类确认为荣；
以创造接口为耻、复用现有为荣；
以跳过验证为耻、主动测试为荣；
以破坏架构为耻、遵循规范为荣；
以假装理解为耻、诚实无知为荣；
以盲目修改为耻、谨慎重构为荣。
