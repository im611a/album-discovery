# Project documentation

Project documentation is split by responsibility:

- [PRODUCT_SPEC.md](./PRODUCT_SPEC.md): approved first-version product rules, navigation, filters, and exclusions
- [INFORMATION_ARCHITECTURE.md](./INFORMATION_ARCHITECTURE.md): route responsibilities and content hierarchy
- [DATA_ARCHITECTURE.md](./DATA_ARCHITECTURE.md): source authority, logical model, provenance, and read-model boundaries
- [NETEASE_CATALOG_STRATEGY.md](./NETEASE_CATALOG_STRATEGY.md): post-feasibility catalog and market-channel strategy
- [NETEASE_FEASIBILITY_PLAN.md](./NETEASE_FEASIBILITY_PLAN.md): 0.15 validation method and 0.16 adoption summary
- [NETEASE_FEASIBILITY_REPORT.md](./NETEASE_FEASIBILITY_REPORT.md): bounded 0.15A experiment evidence and risks
- [NETEASE_REGION_TAXONOMY_REPORT.md](./NETEASE_REGION_TAXONOMY_REPORT.md): bounded 0.15B market-channel and region-signal evidence
- [RYM_IMPORT_STRATEGY.md](./RYM_IMPORT_STRATEGY.md): authorized offline import strategy
- [RYM_TAXONOMY.md](./RYM_TAXONOMY.md): rating and taxonomy semantics
- [OPEN_SOURCE_REFERENCES.md](./OPEN_SOURCE_REFERENCES.md): dated public-repository audit
- [ROADMAP.md](./ROADMAP.md): completed gates, current stage boundaries, and next stop point
- [ALEKSI_CODEX_PLANNING_METHOD.md](./ALEKSI_CODEX_PLANNING_METHOD.md): complete planning method used for repository-wide and cross-file work
- [V0.2_CODE_AUDIT.md](./V0.2_CODE_AUDIT.md): file-based audit of the current v0.2 routes, components, data flow, styles, and tests
- [V0.2_PLAN.md](./V0.2_PLAN.md): executable file-level plan for the remaining v0.2 stages

The product specification owns product scope and names. Information architecture
owns routes and content hierarchy. Data architecture owns field authority and
provenance. Source-specific strategies apply those decisions, while experiment
reports remain immutable evidence rather than product specifications.
