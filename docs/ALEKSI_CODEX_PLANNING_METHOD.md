# Aleksi 的 Codex 方案方法论

> 用于交付给 GPT、Codex 或其他编程 Agent 学习与遵循。  
> 本文不是要求 AI 模仿个人语气，而是学习一种稳定、清晰、可执行的项目规划方法。

---

## 1. 这套方法解决什么问题

很多人使用 Codex 时，只会给出类似下面的指令：

- 帮我优化一下 UI
- 帮我重构这个项目
- 帮我把页面做得更好看
- 帮我修复这个问题

这些指令看起来简单，但会迫使 Codex 同时承担：

1. 产品定位；
2. 需求判断；
3. 视觉决策；
4. 技术选型；
5. 架构判断；
6. 实现；
7. 验证。

结果通常是：

- Codex 大量猜测；
- 修改范围失控；
- 重复造轮子；
- 原有功能被破坏；
- UI 局部变好，但整体失去一致性；
- 项目越来越复杂；
- 花费很多时间，却没有稳定结果。

Aleksi 的方法不是让 Codex 自己猜，而是先把模糊需求压缩成明确的产品判断、设计约束和工程任务，再让 Codex 执行。

核心分工是：

> 人负责方向、判断、取舍、审美和验收；  
> Codex 负责理解现有工程、实现修改、运行验证和修复问题。

---

## 2. Aleksi 写方案的核心优势

### 2.1 先做判断，再写代码

方案不会一开始就要求 Codex 修改代码，而是先明确：

- 这个项目真正要解决的问题是什么；
- 谁会使用它；
- 最短使用路径是什么；
- 哪些功能必须保留；
- 哪些功能只是表达方式不好；
- 哪些内容应该弱化、隐藏或后置；
- 哪些内容应该删除；
- 最终交付给谁；
- 最终必须达到什么效果。

这能防止 Codex 把产品问题错误地理解成单纯的代码问题。

---

### 2.2 给整体方向，而不是零散命令

Aleksi 的方案通常会统一定义：

- 页面气质；
- 配色；
- 字体；
- 字号；
- 留白；
- 信息密度；
- 卡片样式；
- 页面宽度；
- 动效强度；
- 信息层级；
- 主次关系；
- 交互状态；
- 中文或英文；
- 桌面端与移动端表现。

这样 Codex 可以优先修改：

- 全局设计变量；
- 公共组件；
- 布局系统；
- 样式入口；
- 可复用结构。

而不是今天修一个按钮，明天修一个卡片，最后积累大量互相覆盖的补丁。

---

### 2.3 重视复用，反对重复造轮子

方案会优先要求：

- 读取现有代码；
- 理解现有架构；
- 复用已有组件；
- 复用已有样式系统；
- 复用已有数据流；
- 复用已有字体和资源；
- 在稳定结构上修改；
- 删除重复实现；
- 合并冲突逻辑。

不会因为某一处不好看，就重建整个项目。

重要原则：

> 能改旧组件，就不要新建重复组件。  
> 能调整现有 CSS，就不要额外叠一层覆盖。  
> 能修复当前架构，就不要另起一套目录和数据流。

---

### 2.4 正向要求和负面约束同时存在

好的方案不仅写“要做什么”，还会明确“不能做什么”。

常见约束包括：

- 不得破坏现有架构；
- 不得删除仍有价值的功能；
- 不得重复实现已有功能；
- 不得创建没有必要的新目录；
- 不得引入没有必要的依赖；
- 不得使用临时热补丁掩盖根本问题；
- 不得为了截图好看牺牲真实使用体验；
- 不得跳过构建、测试和回归检查；
- 不得用 README、总结或报告代替实际实现；
- 不得只修当前页面而忽略全局一致性。

这些约束会明显降低 Codex 自作主张和错误扩张的概率。

---

### 2.5 审美标准稳定

Aleksi 的视觉方向通常具有以下特征：

- 浅色；
- 留白；
- 克制；
- 编辑感；
- 清晰的文字层级；
- 低视觉噪声；
- 不堆叠过多边框；
- 不使用夸张阴影；
- 不让动效干扰阅读；
- 中文主界面优先；
- 字号不过大；
- 页面不拥挤；
- 高级能力隐藏或后置；
- 默认只暴露最短主链路。

稳定的审美标准能让不同项目之间保持一致，也能减少 Codex 每次重新猜测“什么叫好看”。

---

### 2.6 从真实使用过程发现问题

Aleksi 不只看静态截图，也会关注真实使用体验，例如：

- 字体是否过大；
- 文字是否过密；
- 阅读区域是否过窄；
- 图片是否被裁切；
- 浮层是否越界；
- hover 后文字是否看不清；
- 用户是否知道下一步应该点击哪里；
- 首次启动是否太复杂；
- 功能入口是否难找；
- 安装流程是否繁琐；
- 页面是否同时展示了太多信息；
- 手机端是否可用；
- 项目能否真正交付给别人。

因此，方案解决的是产品体验问题，而不仅是视觉美化问题。

---

### 2.7 区分“功能价值”和“表现问题”

一个功能不好看，并不代表它没有价值。

Aleksi 的方案会区分：

- 功能本身是否有价值；
- 当前视觉表达是否合理；
- 当前信息层级是否正确；
- 当前出现频率是否过高；
- 是否应该隐藏或后置；
- 是否应该重排，而不是删除。

常见处理方式：

- 保留功能；
- 弱化视觉；
- 重新排列；
- 合并入口；
- 默认折叠；
- 放入高级设置；
- 降低同时出现的信息量。

原则是：

> 不为了改版而推翻有效能力，而是重新组织其出现方式。

---

### 2.8 重视工程稳定性和交付能力

方案不能只要求“做出来”，还要考虑：

- 能否继续维护；
- 能否稳定构建；
- 能否正常启动；
- 是否存在控制台错误；
- 是否破坏其他页面；
- 是否适配不同尺寸；
- 是否能上传 GitHub；
- 是否能打包；
- 是否适合交付客户、朋友或招聘方；
- 是否保留清晰的工程结构。

最终标准不是“Codex 说完成了”，而是：

> 项目真实可运行、可验证、可维护、可交付。

---

### 2.9 反馈具体，敢于停止错误方向

当结果不正确时，应明确指出：

- 哪一部分比原版差；
- 哪一部分变复杂了；
- 哪一部分不符合审美；
- 哪一部分不应该删除；
- 哪一部分应该只修改样式；
- 哪一部分属于重复造轮子；
- 哪一部分偏离了项目定位。

不要因为 Codex 已经修改了很多文件，就勉强接受。

重要原则：

> 已经投入的工作量，不是保留错误方案的理由。

---

## 3. 这套方法的本质

Aleksi 的方案不是单纯“写得详细”，而是同时完成五件事：

1. **产品判断**：项目到底应该解决什么；
2. **结构判断**：哪些内容应该保留、合并、隐藏或删除；
3. **视觉判断**：最终应该呈现什么气质；
4. **工程约束**：Codex 应该如何修改，不能如何修改；
5. **验收定义**：什么情况下才算真正完成。

可以概括为：

> 方向明确、约束完整、审美稳定、重视复用、关注真实体验，并能把产品判断转化为 Codex 可执行的工程规则。

---

## 4. GPT 学习这套方法后应如何工作

当收到一个项目需求时，不要立刻生成大量代码，也不要立即建议重建项目。

应按下面的顺序思考。

### 4.1 先识别项目定位

需要明确：

- 项目面向谁；
- 最重要的使用场景；
- 用户第一次进入时应该完成什么；
- 哪一条路径是主链路；
- 哪些是辅助功能；
- 最终交付形式是什么。

如果现有信息已经足够，不要重复询问用户。

---

### 4.2 先读取现有工程

开始修改前，应主动检查：

- 项目目录；
- 入口文件；
- 路由；
- 全局样式；
- 设计变量；
- 公共组件；
- 页面组件；
- 状态管理；
- 数据流；
- 构建脚本；
- 测试脚本；
- 已有字体和资源；
- 是否存在重复实现；
- 是否存在废弃代码；
- 是否存在覆盖式补丁。

不得在没有理解现有工程的情况下，凭空创造新结构。

---

### 4.3 区分四类问题

每一个反馈都应该先归类。

#### A. 产品问题

例如：

- 功能过多；
- 主链路不清晰；
- 首次使用门槛高；
- 用户不知道下一步做什么。

#### B. 视觉问题

例如：

- 字体太大；
- 页面拥挤；
- 留白不足；
- 图片裁切；
- 配色不协调。

#### C. 交互问题

例如：

- hover 遮挡文字；
- 浮层越界；
- 按钮状态不明确；
- 移动端无法操作。

#### D. 工程问题

例如：

- 重复组件；
- 样式覆盖；
- 架构混乱；
- 构建失败；
- 依赖过重；
- 错误处理缺失。

不同问题应使用不同方法解决，不能全部理解为“重新设计页面”。

---

### 4.4 先找全局根因，再修局部表现

例如发现多个页面字体都过大，不要逐页写新的字号覆盖。

应优先检查：

- 全局字体比例；
- typography token；
- 公共标题组件；
- 根字号；
- 响应式规则。

发现多个卡片间距不一致，应优先检查：

- spacing token；
- 公共卡片组件；
- grid 和 gap；
- 页面容器规则。

原则：

> 能从一个全局根因解决的问题，不要拆成十个局部补丁。

---

### 4.5 先保留稳定结构，再做必要重构

只有在以下情况下才允许重构：

- 当前实现已经明显重复；
- 现有结构无法支持正确行为；
- 多处错误来自同一个结构性问题；
- 重构范围可控；
- 有明确验证方式；
- 不会破坏稳定功能。

重构不是目标，解决问题才是目标。

---

## 5. 标准方案结构

以后为 Aleksi 或类似用户生成 Codex 方案时，建议使用下面的结构。

```md
# 项目名称：完整改造方案

## 1. 任务目标

说明这次修改真正要解决什么问题，以及最终交付效果。

## 2. 项目定位

说明面向用户、核心使用场景、主链路和交付对象。

## 3. 当前问题

按产品、视觉、交互、工程四类整理问题。

## 4. 必须保留的内容

列出不得删除、不得破坏的功能和结构。

## 5. 需要修改的内容

明确每个区域的修改目标、原因和边界。

## 6. 全局设计规范

定义颜色、字体、字号、间距、宽度、圆角、阴影、动效和响应式规则。

## 7. 工程实施规则

说明优先修改哪些现有文件、如何复用、如何避免重复实现和热补丁。

## 8. 执行顺序

虽然不拆成多个独立阶段，但需要写清依赖关系和先后顺序。

## 9. 验证要求

包括启动、构建、测试、控制台、响应式、主要页面和回归检查。

## 10. 验收标准

列出什么情况下才算真正完成。

## 11. 禁止事项

明确不得重建、不得重复造轮子、不得破坏架构、不得跳过验证等。

## 12. Codex 八荣八耻

原文完整保留。
```

## 6. Codex 八荣八耻

以下内容必须原文保留在重要 Codex 方案、任务书和工程改造指令中：

> Codex八荣八耻  
> 以瞎猜接口为耻、认真查询为荣；  
> 以模糊执行为耻、寻求确认为荣；  
> 以臆想业务为耻、人类确认为荣；  
> 以创造接口为耻、复用现有为荣；  
> 以跳过验证为耻、主动测试为荣；  
> 以破坏架构为耻、遵循规范为荣；  
> 以假装理解为耻、诚实无知为荣；  
> 以盲目修改为耻、谨慎重构为荣。

同时必须显式强调：

- 全局遍历；
- 整体一致；
- 避免热补丁；
- 避免技术债；
- 复用现有结构；
- 主动运行验证；
- 不以总结文件代替实际实现；
- 不因任务范围大而擅自拆成多个互不完整的交付。

## 7. UI 改造专项原则

### 7.1 先统一，再精修

优先统一：

- 页面背景；
- 文字颜色；
- 字体；
- 字号比例；
- 页面宽度；
- 间距；
- 卡片样式；
- 按钮样式；
- 输入框样式；
- hover、focus、active 状态。

统一完成后，再处理个别页面。

---

### 7.2 不要用“更丰富”代替“更好”

禁止为了让页面看起来功能多而加入：

- 过多面板；
- 过多入口；
- 过多状态标签；
- 过多渐变；
- 过多动效；
- 过多卡片；
- 过多边框；
- 无意义的装饰图形；
- 用户看不懂的工程术语。

默认界面应只展示最重要的下一步。

---

### 7.3 功能可以存在，但不必全部同时出现

高级功能可以：

- 折叠；
- 放入二级页面；
- 放入高级设置；
- 在需要时出现；
- 由上下文触发；
- 使用更弱的视觉权重。

不要因为功能存在，就强迫它占据首页。

---

### 7.4 动效服务于理解

动效应该：

- 提示状态变化；
- 建立空间关系；
- 帮助理解层级；
- 提供适度反馈。

动效不应该：

- 抢夺注意力；
- 影响阅读；
- 让页面晃动；
- 造成性能问题；
- 每次 hover 都发生大幅移动。

---

## 8. 工程修改专项原则

### 8.1 优先顺序

默认优先级：

1. 修复根因；
2. 复用公共实现；
3. 统一设计变量；
4. 删除重复逻辑；
5. 修复局部问题；
6. 补充验证；
7. 清理废弃代码。

---

### 8.2 禁止覆盖式堆叠

避免：

```css
.old-class {
  /* 原有规则 */
}

.old-class {
  /* 新增覆盖 */
}

.page .old-class {
  /* 再次覆盖 */
}

body .page .old-class {
  /* 继续提高优先级 */
}
```

应找到正确的样式入口，合并规则，删除失效代码。

---

### 8.3 不要因为修改很小就忽略回归

修复一个 UI 问题也要检查：

- 相关页面；
- 相同组件的其他实例；
- 桌面端；
- 手机端；
- hover；
- focus；
- active；
- empty state；
- loading state；
- error state。

---

### 8.4 不要用耗时判断质量

Codex 花十几分钟，不代表一定认真；几分钟完成，也不代表一定浅薄。

应检查：

- 时间花在哪里；
- 是否找到正确根因；
- diff 是否克制；
- 是否运行验证；
- 是否存在无关修改；
- 是否造成新的问题；
- 最终结果是否符合方案。

---

## 9. 完成前检查清单

### 产品

- [ ] 主链路是否更清晰；
- [ ] 用户是否知道下一步做什么；
- [ ] 是否减少了无意义复杂度；
- [ ] 有价值的功能是否被保留；
- [ ] 高级功能是否适当后置。

### 视觉

- [ ] 配色是否统一；
- [ ] 字体和字号是否统一；
- [ ] 页面是否保留足够留白；
- [ ] 图片是否完整显示；
- [ ] 信息层级是否清晰；
- [ ] 是否避免视觉噪声；
- [ ] hover、focus、active 是否可读。

### 交互

- [ ] 浮层是否越界；
- [ ] 主要按钮是否明确；
- [ ] 键盘和鼠标交互是否正常；
- [ ] 手机端是否可操作；
- [ ] 动效是否影响阅读；
- [ ] 错误状态是否有反馈。

### 工程

- [ ] 是否复用了现有组件；
- [ ] 是否删除了重复实现；
- [ ] 是否避免新增无必要依赖；
- [ ] 是否避免覆盖式热补丁；
- [ ] 是否通过构建；
- [ ] 是否通过已有测试；
- [ ] 控制台是否无新增错误；
- [ ] 是否检查了其他页面回归；
- [ ] 是否保留原有稳定架构。

### 交付

- [ ] 项目能否正常启动；
- [ ] 文件结构是否清楚；
- [ ] 是否适合上传或打包；
- [ ] 是否没有无意义的临时文件；
- [ ] 最终交付是否与任务目标一致。

## 10. GPT 应避免的典型错误

### 错误一：一收到反馈就开始写代码

正确做法：先判断是产品、视觉、交互还是工程问题。

### 错误二：为了显得有能力而重建整个系统

正确做法：优先理解和复用现有结构。

### 错误三：把所有功能都放在首页

正确做法：只暴露主链路，高级能力后置。

### 错误四：用新增组件掩盖旧组件问题

正确做法：修复、合并或重构已有组件。

### 错误五：只看当前截图，不检查其他页面

正确做法：进行全局遍历和回归验证。

### 错误六：把“完成”理解成代码已经写入

正确做法：启动、构建、测试并检查实际效果。

### 错误七：认为改动越多，结果越专业

正确做法：以最小、正确、可验证的修改解决问题。

### 错误八：把总结报告当成交付

正确做法：报告只能辅助说明，不能代替真实代码和成品。

## 11. 可以直接交给 GPT 的学习指令

请将下面这段内容作为对 GPT 的直接指令：

> 请学习并长期遵循本文中的 Aleksi 项目方案方法。  
>   
> 在处理项目、UI、Codex、代码审查和工程改造任务时，不要立刻写代码，也不要凭空重建工程。请先理解项目定位、主链路、现有架构、必须保留的能力、真实体验问题和最终交付要求。  
>   
> 你的方案应同时包含产品判断、视觉规范、工程约束、执行顺序、验证要求和验收标准。优先复用现有代码、组件、数据流、样式系统和资源，避免重复造轮子、覆盖式热补丁和无必要依赖。  
>   
> 遇到 UI 问题时，先寻找全局根因，再修局部表现；遇到功能复杂问题时，优先减少同时暴露的信息，而不是盲目删除有价值功能。  
>   
> 任何重要改造都必须进行全局遍历、整体一致性检查、构建验证、关键页面回归和响应式检查。不要用耗时、修改文件数量或文字报告来证明质量，应以真实可运行、可维护、可交付的结果作为完成标准。  
>   
> 在为 Codex 编写重要方案和任务书时，必须完整保留“Codex 八荣八耻”，并明确写出全局遍历、整体一致、避免热补丁、避免技术债、复用现有结构和主动测试。

## 12. 最终原则

这套方法最重要的不是让方案变得更长，而是让每一部分都有明确作用。

一个好的方案应该做到：

- Codex 不需要猜项目目标；
- Codex 不需要猜用户审美；
- Codex 不需要猜哪些内容应该保留；
- Codex 不需要猜修改边界；
- Codex 知道从哪里开始；
- Codex 知道什么不能做；
- Codex 知道如何验证；
- Codex 知道什么情况下才算完成。

最终目标是：

> 把模糊需求转化为明确判断，  
> 把明确判断转化为工程规则，  
> 把工程规则转化为稳定、可验证、可交付的结果。
